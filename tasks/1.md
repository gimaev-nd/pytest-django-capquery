# Создать библиотеку для ускорения тестов django.

Это плагин для pytest. Он следит за sql-запросами к БД, запоминает их и их результаты (далее capquery, сокращение от capture query) в текстовых файлах.
При повторном запуске тестов, проверяется, есть этот sql-запрос среди сохранённых capquery и если есть, то результат возвращается из него, а не из БД.
Поддерживается только postgres.

## Результат задачи (критерий «сделано»)

Полноценная библиотека:

- код плагина (дистрибутив `pytest-django-capquery`, импортируемый модуль `capquery` — по имени репозитория);
- тесты самого плагина;
- README и докстринги;
- CI (GitHub Actions) с сервис-контейнером postgres;
- демо-проект в репозитории для интеграционных тестов;
- бенчмарк-тест, показывающий ускорение прогона на реплее.

## Совместимость и зависимости

- Python ≥ 3.10;
- Django 4.2 LTS и 5.x;
- pytest ≥ 7, pytest-django ≥ 4.5;
- runtime-зависимости: `pytest-django`, `PyYAML`;
- поддерживается только postgres;
- библиотека не работает с БД напрямую, а использует механизмы pytest-django.

## Границы применимости

- Капчурятся и подменяются **все запросы к данным**, а не только SELECT: `SELECT`, `WITH`, `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `TRUNCATE`, `VALUES`, `TABLE`, а также `executemany` целиком. У записи хранится и результат (`RETURNING`-строки), и `rowcount` — именно его Django возвращает из `QuerySet.update()`/`QuerySet.delete()`.
- Запрос ищется по **порядковому номеру** в контексте (тест или фаза миграций), а **хеш sql** сверяется как проверка правильности: запись на позиции отдаётся, только если это тот же запрос. Параметры не участвуют ни в ключе, ни в проверке (см. «Хеширование и поиск»).
- **Не капчурятся и всегда выполняются реально:** DDL схемы (`CREATE`/`ALTER`/`DROP` — тестовая база действительно создаётся и действительно получает схему проекта) и всё, что не является запросом к данным: управление транзакциями (`SAVEPOINT`, `RELEASE`, `SET CONSTRAINTS`), обслуживание (`VACUUM`, `ANALYZE`), администрирование, а также всё нераспознанное. Консервативность здесь намеренная: неизвестный запрос никогда не подменяется, поэтому его побочный эффект не может потеряться. Такие запросы не занимают позицию в контексте: файл capture содержит только запросы к данным.
- Служебная таблица Django `django_migrations` — во второй группе, хотя это обычный `INSERT`: в параметрах пишется момент применения миграции, поэтому захваченная запись содержала бы время того прогона, который её записал, и файл менялся бы при каждой записи. Чтения `django_migrations` при этом подменяются как обычно, с фиксированными часами в колонке `applied`.
- Следствие: на реплее БД не содержит того, что «записали» подменённые запросы. Поэтому плагин не пишет captures в сеансе, где тест реально сходил в БД (см. «Поведение», п. 5), а фаза миграций выполняется реально, если в сеансе есть хоть один такой тест (см. «Миграции»).
- Что капчурить нельзя по природе: тесты, ожидающие ошибку от БД (`IntegrityError`) — записываются только успешные запросы. Такие тесты помечаются `capquery_ignore`. Значения, меняющиеся каждый прогон (`auto_now_add`, `uuid4` по умолчанию, `timezone.now`), капчурингу больше не мешают: они не входят в ключ поиска.
- Библиотека должна работать, только если тестов много: тестов, требующих БД (`db`/`django_db`), после применения `-k`/`-m` / `--lf` — больше пяти. Иначе плагин неактивен целиком (ни сбора, ни подмены).
- Капчуринг включается автоматически для всех тестов, использующих `db`/`django_db`; исключить тест — маркером `@pytest.mark.capquery_ignore`.
- Параллельные прогоны (`pytest-xdist`) не поддерживаются: при `-n` плагин отключается целиком с предупреждением, тесты идут в БД.
- Тесты с `transaction=True` (TransactionTestCase) — открытый вопрос, см. «Что нужно исследовать».

| Что | CLI | ini | env | по умолчанию |

| лимит перегенераций теста | `--capquery-max-attempts=N` | `capquery_max_attempts` | `CAPQUERY_MAX_ATTEMPTS` | 3 |

Приоритет источников: CLI > env > ini. Условие включения: число DB-тестов **строго больше** `capquery_min_tests`.

## Как работает перехват

Патчим `django.db.backends.utils.CursorWrapper` — прокси-курсор: перехватываем `execute`/`executemany` и `fetchall`/`fetchone`/`fetchmany`, подменяем также `description` и `rowcount`. База по-прежнему postgres.

Почему не публичный `connection.execute_wrapper`: его возвращаемое значение игнорируется (`CursorWrapper._execute_with_wrappers` возвращает результат `_execute`, а код-вызывающий затем читает строки из реального курсора), поэтому подменить результат через публичный API нельзя — реплей без патча курсора технически невозможен.

Два режима:

- **сбор (recording)** — запрос уходит в postgres, запрос и его результат (строки + `rowcount`) записываются;
- **реплей (replay)** — запрос ищется в хранилище; при попадании в postgres не уходит вообще, результат отдаётся из capquery. Для записи это означает, что `INSERT` не выполняется, а его `RETURNING`-идентификатор берётся из записи; `UPDATE`/`DELETE` возвращают записанный `rowcount`.
- **passthrough** — запрос выполняется реально и не записывается (тест помечен `capquery_ignore`, тест нестабилен, либо это DDL/управление транзакциями).

## Хранение

Собранные записи и их результаты сохраняются в папке `captures` рядом с тестами, в формате yaml.

Раскладка (пути относительно `pytest rootdir`): один yaml на тест — `tests/captures/<путь модуля>/<имя теста>.yaml`, внутри — список записей. Для параметризованного теста в имя файла добавляется id параметра. Имя строится из node id с санитизацией недопустимых символов — нужно позаботиться о том, чтобы не было конфликтов имён. Можно посмотреть, как это сделано в https://github.com/vberlier/pytest-insta.

Captures миграций — один общий файл `captures/migrations.yaml` в корне проекта, без разбивки по миграциям (миграции не привязаны к тесту).

Схема файла (пример `tests/captures/shop/test_orders.py/test_create.yaml`):

```yaml
captures:
  - n: 1                 # порядковый номер запроса в тесте — ключ поиска
    hash: "9f2c…"        # sha256 от sql — проверка правильности запроса на этой позиции
    sql: "SELECT id, name FROM shop_order WHERE id = %s"
    schemas: {params: 1, rows: 2}
    params: [1]
    rowcount: 2          # строк у SELECT, затронутых строк у записи
    columns: ["id", "name"]
    rows:
      - [1, "первый"]
      - [2, null]
schemas:
  1: [int]
  2: [int, str]
```

На верхнем уровне два поля: `captures` — запросы с их результатами, `schemas` — схемы данных. Данные пишутся как есть, без обёртки с типом; схема — массив типов одного поля (элемент на параметр, элемент на колонку строки), тип значения — элемент схемы на его позиции. Capture ссылается на схемы своих полей по id (`schemas: {params: 1, rows: 2}`), а таблица `schemas` хранит каждую схему один раз: одинаковые схемы получают один id и в корне не дублируются.

Типы: `int`, `str`, `bool`, `float`, `decimal`, `date`, `time`, `datetime`, `timedelta`, `uuid`, `bytes`, `list`, `tuple`, `dict`, `null`. `bytes` → base64, `Decimal` → строка, `NaN`/`Infinity` → строки. Тип, который по данным не отличить от строки (`decimal`, даты и время, `uuid`, `bytes`), берётся только из схемы. Контейнер описывается своим видом: `{list: [int, str]}`, `{tuple: [int]}`, `{dict: {key: int}}`. `NULL` в данных пишется как `null` и отдельного типа не требует: колонка, где всё `null`, описывается как `null`. У `executemany` в `params` лежат наборы параметров, поэтому его схема перечисляет схемы наборов: `1: [[str, int], [str, int]]`.

## Хеширование и поиск

Ключ поиска — **порядковый номер запроса в контексте** (первый запрос к данным в тесте, второй и так далее), а **хеш считается только от sql** и служит проверкой правильности: он отвечает на вопрос «тот ли это запрос, что записан на этой позиции».

```text
n     = порядковый номер запроса среди капчурируемых запросов контекста (1 для первого)
hash  = sha256(sql.encode("utf-8"))
запись на позиции n отдаётся, только если её hash совпал с хешем пришедшего запроса
```

Параметры не участвуют ни в ключе, ни в проверке: они пишутся в capture как данные (для читателя файла и для диагностики) и не сверяются. Поэтому:

- значение, новое в каждом прогоне (`auto_now_add`, `uuid4` по умолчанию, `timezone.now`, список `IN (...)` из `set`) не делает запрос ненаходимым: это тот же запрос на той же позиции, и строки возвращаются из capture;
- запрос, выполненный несколько раз подряд, — это просто разные позиции контекста, отдельный счётчик на запрос не нужен;
- проверка позиционная: если тест изменился, на позиции окажется другой запрос. Это **промах**, как и запись, которой на позиции нет: запрос уходит в БД, тест перезапускается и capture перегенерируется (правило 2), а в отчёте такие случаи считаются отдельно — `N statement(s) did not match the query captured at their position`.

Цена позиционного ключа — порядок запросов в тесте должен сохраняться: правка, сдвигающая позиции, перегенерирует capture теста целиком, а не одну запись.

Ключ `(порядковый номер, хеш sql)` пришёл на смену хешу пары `(sql, params)` по мотивам https://github.com/Suor/django-cacheops (там это `cacheops/query.py:_cache_key`, md5 от sql с подставленными параметрами): хеш по параметрам делал запрос ненаходимым в каждом прогоне, если среди параметров есть значение, меняющееся от прогона к прогону. Как зависимость или копия кода cacheops не используется.

## Хранилище: in-memory sqlite

При повторном запуске нужно собрать все данные из тестов и сложить их в inmemory sqlite. Далее вся работа ведётся только с sqlite: yaml-файлы читаются один раз при старте сеанса, а не на каждый запрос. Схема таблицы:

```
captures(ctx TEXT, n INTEGER, hash TEXT, sql TEXT, params TEXT, rowcount INTEGER, columns TEXT, rows BLOB, PRIMARY KEY (ctx, n))
```

Поиск — по позиции `n` (в границах контекста `ctx`); `hash` хранится, чтобы сверить запись с пришедшим запросом, а `sql` — для диагностики.

## Повторные обращения к одному запросу

Если в одном тесте один и тот же запрос выполнился несколько раз и вернул разные строки (например между двумя SELECT был INSERT), это просто разные позиции контекста: первый SELECT — позиция 1, второй — позиция 2. Никакого отдельного списка результатов на один запрос не нужно, порядок исполнения задаётся номерами.

## Миграции

- Фаза миграций капчурится и подменяется целиком, как обычный тест: чтения executor-а `django_migrations` и прочие SELECT, а также `INSERT`-ы сидов (DML миграций). DDL при этом всегда выполняется реально — схема в базе настоящая, поэтому запрос, которого нет в captures, всё равно попадает в рабочую базу.
- Границей фазы является вызов `django.test.utils.setup_databases`, а не `MigrationExecutor.migrate`: пост-миграционный сигнал (`migrate` вызывает его после executor-а) порождает запросы уже вне executor-а, и без расширения границы они попадали бы в captures первого теста сеанса.
- Пост-миграционный сигнал (content types и permissions) исключён из captures и всегда выполняется реально: он строит список параметров `IN (...)` из `set`, порядок параметров зависит от `PYTHONHASHSEED`, поэтому файл, записанный одним процессом, отличался бы от файла, записанного другим; а поскольку запрос ищется по позиции, запрос, появившийся в одном процессе и отсутствующий в другом, сдвинул бы позиции всех последующих.
- Для миграций действует то же правило перегенерации, что и для тестов: если не удалось выполнить всё через capture-кеш — фаза миграций прогоняется с начала без кеша, с обновлением `captures/migrations.yaml`.
- Фаза выполняется реально (и записывается заново), если в сеансе есть хоть один тест, который пойдёт в БД по-настоящему: тест без captures, тест, помеченный нестабильным, или тест с `capquery_ignore`. Такой тест должен видеть данные, которые пишут миграции, а не пустую базу. Тест, который вообще не делает капчурируемых запросов, запоминается в state-файле (`captures_nothing`) и фазу реальной не держит.
- Фаза подменяется только когда тестовая база создаётся с нуля: при `--reuse-db` с уже существующей базой состояние не соответствует записи (executor принял бы решение по подменённым чтениям), поэтому фаза идёт реально. Проверяется наличием `test_<db>` через `pg_database`, а не значением флага `--reuse-db`.
- `setup_databases` может вызваться в одном процессе дважды: если перезапускаемый тест оказался последним в сеансе, pytest сносит session-фикстуры после первой попытки, и повторная попытка поднимает фикстуру pytest-django заново. `create_test_db` префиксует то имя, которое находит в настройках, поэтому второй вызов создал бы `test_test_<db>` — вторую базу, о которой сеанс ничего не знает, с подменённой (то есть пустой по данным) фазой. Перед каждым вызовом имя из настроек возвращается на место — так же, как это делает teardown Django перед удалением базы.

## Сброс счётчиков БД

Чтобы capquery постоянно не менялись и не портили merge requests, нужно сбрасывать счётчики БД, чтобы id всех сущностей начинались с 1. Для этого к тестовой базе нужно применить команду django `sqlsequencereset`, делать это нужно **до применения миграций**.

При создании тестовой базы с нуля таблиц ещё нет — команда вернёт пустой набор, и счётчики и так начинаются с 1: это нормальная ситуация, обрабатывается молча, без ошибки. Реальный эффект сброс даёт на переиспользуемой базе (`--reuse-db`) и при повторных прогонах.

## Поведение

1. Если для теста нет capquery, то в случае успешного выполнения теста capquery создаётся.
2. Если для теста есть все capquery, но какой-то запрос ушёл в БД (не нашёлся подходящий capquery или на его позиции записан другой запрос), то тест нужно перезапустить и, в случае успеха, сформировать capquery снова.
3. Если для теста есть все capquery, и он упал, то тест нужно перезапустить и, в случае успеха, сформировать capquery снова.
4. Если для теста есть все capquery, и какой-то запрос ушёл в БД, но записать новые captures нельзя (см. п. 5), тест не перезапускается: старые captures остаются, тест попадает в отчёт, а следующий сеанс выполняет фазу миграций реально и перегенерирует captures.
5. Запись никогда не делается поверх captures в сеансе, где фаза миграций была подменена, а тест при этом реально сходил в БД (не нашёл запрос в captures): такая запись содержала бы ответы базы, которой миграции ничего не писали. В этом случае фаза миграций сначала выполняется реально (база пересоздаётся и мигрируется без кеша), и только потом тест перезапускается. Если пересоздать не удалось — captures не трогаются, и это состояние помечается в state-файле (`requires_real`), чтобы следующий сеанс сделал фазу реальной.

Перезапуск делается своими силами, без внешних зависимостей: плагин собирает помеченные тесты и перезапускает их внутри того же pytest-сеанса с отключённым кешем. Схема «всегда два полных прохода» не используется.

## Отслеживание перегенераций

Нужен механизм отслеживания перегенераций, чтобы не пытаться генерировать capquery для тестов, для которых нельзя сгенерировать стабильные capquery.

- Лимит попыток на тест настраиваемый, по умолчанию 3 (`--capquery-max-attempts`).
- Счётчик персистентный, чтобы работал и между прогонами: state-файл `captures/.capquery-state.yaml` с соответствием `node_id` → `{attempts, unstable, requires_real, captures_nothing}`. Запись с ключом фазы миграций (`requires_real`) просит следующий сеанс выполнить миграции реально; `captures_nothing` отмечает тест, который не выдал ни одной записи.
- При исчерпании лимита тест помечается «нестабильный»: его captures удаляются, и дальше он всегда выполняется по-настоящему, без подмены. Пометка сохраняется в state-файле и попадает в отчёт в конце сеанса.

## Что нужно исследовать в рамках задачи

- Последствия подмены чтений `django_migrations`: executor может решить, что миграции уже применены, а DDL при этом выполняется реально — база может остаться без таблиц. **Решено:** фаза подменяется только на базе, созданной с нуля (проверяется наличием `test_<db>`), иначе выполняется реально; см. README, «Problems of caching the migration phase».
- Прочие проблемы из-за кеширования миграций: `--reuse-db`, повторные прогоны, падение между фазой миграций и фазой тестов. **Решено частично:** `--reuse-db` с существующей базой → фаза реальная; промах при подмене фазы → фаза переделывается без кеша; пост-миграционный сигнал исключён из captures (порядок параметров из `set` не воспроизводим).
- Тесты с `transaction=True` (TransactionTestCase): между тестами чистятся таблицы и сбрасываются последовательности — капчурить ли их и как это стыкуется со сбросом счётчиков через `sqlsequencereset`.
- Асинхронные тесты и тесты с несколькими БД (`db_alias`): хеш и хранилище должны различать базы, либо такие тесты капчуриться не будут.

## Критерии приёмки

- Демо-проект в репозитории + тесты плагина через `pytester`; CI на GitHub Actions с сервис-контейнером postgres.
- Отдельный бенчмарк-тест, показывающий ускорение прогона на реплее.
- Функциональные проверки:
  - первый прогон создаёт `tests/captures/*.yaml` и `captures/migrations.yaml` в описанном формате;
  - второй прогон не отправляет в postgres **ни одного запроса к данным — ни чтения, ни записи** (счётчики плагина: `missed == 0` и `executed against postgres == 0`), но тесты проходят; отдельно проверяется прямым подключением драйвером, что БД действительно не получила ни сиды миграций, ни записи тестов;
  - запись, выполненная в тесте (`create` с `RETURNING`, `update`/`delete` с `rowcount`, `bulk_create`, сырой `INSERT ... RETURNING`, `executemany`), на реплее возвращает то же, что вернула при записи;
  - изменение запроса в тесте → captures теста обновляются по правилу 2/3, лишние записи не остаются; отдельно проверяется, что расхождение на позиции обнаружено как несовпадение хеша (`N statement(s) did not match the query captured at their position`), и что запрос с параметром, новым в каждом прогоне, всё равно подменяется;
  - тест с нестабильными результатами → не более `capquery_max_attempts` перегенераций, затем captures удалены, тест помечен нестабильным и идёт в БД;
  - при числе DB-тестов ≤ 5 плагин неактивен;
  - при запуске с `-n` плагин отключается с предупреждением;
  - `@pytest.mark.capquery_ignore` исключает тест из капчуринга;
  - `sqlsequencereset` применяется до миграций и не падает на пустой/свежей базе.
